## Intent

**Problem:** The tools hub has four live tools (EMI, Area Unit Converter, Stamp Duty, Rent vs. Buy). "Rental yield" is named only in the brief's Scope §5 ("Fill over time") with no registry stub and no detail — a buyer evaluating an income property has no way to see the honest, cost-adjusted yield on their own numbers, only the bare gross-rent-over-price ratio most sites quote.

**Approach:** Originate the registry entry from scratch and build one self-contained tool module riding the existing chassis exactly like `rent-vs-buy`: a pure `compute()` that returns gross yield, an honest unleveraged net yield (rent minus property tax, maintenance, society charges, and a vacancy allowance — all adjustable, none hardcoded), a brief benchmark-context sentence against India's commonly-cited gross-yield range, and — only when the user opts into an off-by-default leverage toggle — a leveraged net yield (net yield minus year-1 loan interest) and a cash-on-cash return (net cash flow after the full EMI, over actual cash invested). The leverage piece reuses `emi/compute.ts`'s `compute()` directly, exactly as `rent-vs-buy` does. Ship directly as `phase: 1`.

## Boundaries & Constraints

**Always:**
- Mirror module shape: `src/lib/tools/rental-yield/{compute.ts,schema.ts}` (pure) + `src/components/tools/rental-yield/Tool.tsx` (`'use client'`). No `data.ts` — every rate here (property tax %, maintenance %, society charges, vacancy months, down payment %, loan rate/tenure, acquisition costs %) is a user-supplied assumption or a genuinely adjustable input, not a sourced statutory fact (AD-6 territory only covers hardcoded rates in `compute.ts`, not UI defaults) — same rationale `rent-vs-buy/compute.ts`'s header comment documents.
- Reuse `emi/compute.ts`'s exported `compute(input: EmiInput): EmiResult` directly for the loan piece when leverage is enabled — call it once with `{ principal: loanAmount, annualRate, tenureMonths: tenureYears*12 }` and consume `result.emi` and `result.schedule[i].interest` (first up-to-12 rows) for the year-1 interest figure. Do not reimplement EMI/amortization math a third time. Zero edits to `emi/compute.ts`.
- **Exact algorithm** (implement precisely; do not deviate without a Spec Change Log entry):
  ```
  annualRent            = monthlyRent * 12
  annualPropertyTax     = propertyPrice * propertyTaxPct/100
  annualMaintenance     = propertyPrice * maintenancePct/100
  annualSocietyCharges  = societyChargesMonthly * 12
  annualVacancyCost     = monthlyRent * vacancyMonths
  annualOperatingCosts  = annualPropertyTax + annualMaintenance + annualSocietyCharges + annualVacancyCost
  netAnnualIncome       = annualRent - annualOperatingCosts
  grossYieldPct         = propertyPrice > 0 ? (annualRent / propertyPrice) * 100 : 0
  netYieldPct           = propertyPrice > 0 ? (netAnnualIncome / propertyPrice) * 100 : 0
  benchmarkNote         = sentence comparing grossYieldPct to the ~2-3% typical-India reference band (below/within/above), hedged as a general range not an official stat (see Design Notes for exact phrasing register)

  // Only when leverage === "on":
  downPayment           = propertyPrice * downPaymentPct/100
  loanAmount            = propertyPrice - downPayment
  { emi, schedule }     = computeEmi({ principal: loanAmount, annualRate, tenureMonths: tenureYears*12 })
  annualEmi             = emi * 12
  year1Interest         = sum of schedule[0..min(11, schedule.length-1)].interest   // handles tenure < 1yr and loanAmount=0 (empty schedule -> 0) safely
  netYieldLeveragedPct  = propertyPrice > 0 ? ((annualRent - annualOperatingCosts - year1Interest) / propertyPrice) * 100 : 0
  acquisitionCosts      = propertyPrice * acquisitionCostsPct/100
  actualCashInvested    = downPayment + acquisitionCosts
  annualNetCashFlow     = netAnnualIncome - annualEmi
  cashOnCashReturnPct   = actualCashInvested > 0 ? (annualNetCashFlow / actualCashInvested) * 100 : 0
  // When leverage === "off": downPayment/loanAmount/emi/annualEmi/year1Interest = 0, and
  // netYieldLeveragedPct/annualNetCashFlow/actualCashInvested/cashOnCashReturnPct = null
  // (null, not 0 — distinguishes "not computed because leverage is off" from a genuine zero result).
  ```
  `netYieldPct` (unleveraged) is the honest default and must never subtract loan interest regardless of any other input — only `netYieldLeveragedPct` may include it, and only when `leverage === "on"`.
- Benchmark the **gross** yield against the ~2–3% reference band, not net — this is the figure actually commonly cited for Indian residential yields (matches `rent-vs-buy`'s own FAQ #2 precedent citing "~2–3.5%" as a gross rent-to-price ratio); net yield is shown as its own clearly-labeled "after real costs" number without inventing a second, unsourced net-yield benchmark to compare it against.
- `propertyTaxPct`, `maintenancePct`, `societyChargesMonthly`, `vacancyMonths` are all genuinely adjustable inputs with sane India-convention defaults (maintenance default `1`, matching `rent-vs-buy/schema.ts`'s `maintenancePct` precedent) — never hardcoded constants in `compute.ts`.
- The leverage toggle: no boolean/checkbox/switch component exists in this codebase (confirmed by investigation — no `type="checkbox"`, no `z.boolean()`, no `role="switch"` anywhere under `src/components/tools/` or `src/lib/tools/`). Use a `leverage: z.enum(["off","on"])` field (mirrors `emi/schema.ts`'s `prepayMode` enum-with-off-state precedent most closely) rendered as a single self-toggling pill `<button>` using the exact unselected/selected class pair already established in `emi/Tool.tsx`'s prepayment-mode pills (`border-line text-ink/60` unselected vs `border-gold bg-gold/15 text-ink` selected) — do not invent a new switch/checkbox primitive.
- For **every** numeric field, the zod schema's `.min()/.max()` and the `Slider`'s UI `min/max` must derive from the **same** constant — one `rentalYieldBounds` object in `schema.ts` feeding zod validation, every `Slider`'s props, and `compute.ts`'s defensive clamps (mirrors `rent-vs-buy`'s three-consumer bound-sharing pattern, which itself closed the stamp-duty-rj-class bound-drift defect).
- Reuse `useToolState`, `format.ts` (`inr`/`inrCompact`/`num`), `Slider`, `InputField`, `ResultCard`, `ToolShell` as-is (AD-5, AD-8). `Select.tsx` is not used — it is a `<select>` dropdown, not a toggle, and every input here is either numeric or the one binary leverage state (handled by the pill button above), so there is no genuine 3+-option field.
- Progressive disclosure: `propertyPrice` and `monthlyRent` always visible; `propertyTaxPct`, `maintenancePct`, `societyChargesMonthly`, `vacancyMonths` collapsed behind a "Costs & assumptions" `<details>` (mirrors `rent-vs-buy`'s "Assumptions" section, including its print-visibility CSS fix — apply the same scoped `@media print` rule so "Download PDF" never silently drops the cost assumptions behind a collapsed section); the leverage pill sits below that, and `downPaymentPct`/`annualRate`/`tenureYears`/`acquisitionCostsPct` render only when `leverage === "on"` (mirrors EMI's prepayment-reveal pattern).
- **Honesty/disclaimer requirement:** near the result, in the same position/tone/class as EMI's and rent-vs-buy's disclaimer (`font-body text-cream/45 mt-5 text-xs leading-relaxed`, last content block before `ResultActions`), state that (a) every figure in "Costs & assumptions" (and the loan fields, if leverage is on) is a user-adjustable input, not a sourced fact; (b) the ~2–3% benchmark band is a general, informally-cited reference range, not an official statistic, and will vary by city/market; (c) this tool does not model income tax on rental income, capital gains on eventual sale, or negotiated/below-market rent. Do not overstate precision on the benchmark figure (no "exactly," no false single-decimal authority on the band itself).
- Registry entry (`src/lib/tools/registry.ts`, new row, `phase: 1` immediately):
  - `slug: "rental-yield"`, `category: "finance"`
  - `title: "Rental Yield Calculator"`

  - `seo.h1: "Rental Yield Calculator"`
  - `seo.description: "Calculate gross and net rental yield on an Indian property — factoring in property tax, maintenance, society charges and vacancy — plus cash-on-cash return if you finance it with a home loan. See how your number compares to India's typical rental yield range."`
  - `seo.faq`: at least these two —
    1. "What's the difference between gross and net rental yield?" → gross = annual rent ÷ price; net subtracts the real annual running costs (property tax, maintenance, society charges, a vacancy allowance) before dividing, so it reflects what an owner actually keeps — net is always lower than gross and is the more honest number for comparing an income property.
    2. "Why are Indian residential rental yields so low?" → cite the commonly-quoted ~2–3% gross range as an informal, widely-varying market figure (not an official stat), and invite the user to compare their own number and adjust city/property-specific assumptions.

## Design Notes

- **Why benchmark gross, not net, against the ~2–3% band:** that figure is what's actually commonly cited for Indian residential yields (a simple rent-to-price ratio), and it's the same framing `rent-vs-buy`'s own FAQ #2 already uses ("annual rent is often only around 2–3.5% of a property's value"). Inventing a comparable "typical net yield" band would require a second, less-defensible sourced figure — net yield is instead presented as its own honest, uncompared number, consistent with "don't overstate precision on this benchmark figure."
- **Why leverage-only fields are `null`, not `0`, when leverage is off:** a `0%` cash-on-cash return reads as "this investment breaks even," which is false when the field was simply never computed. `null` lets the UI distinguish "not applicable" from "computed to zero" (the 100%-down-payment edge case genuinely does compute real, non-null leveraged numbers that happen to reduce to the unleveraged ones).
- **Two distinct "with a loan" numbers, deliberately not conflated:** `netYieldLeveragedPct` still divides by the *full property price* (only the interest expense changes) — it answers "how does financing affect the yield-on-the-whole-asset number." `cashOnCashReturnPct` divides by *actual cash invested* (down payment + acquisition costs) and subtracts the *full EMI* (interest + principal) — it answers "how is my own cash doing." These intentionally diverge sharply under leverage (see the leveraged-default I/O row: −5.97% vs. −32.87%) and the UI must label them distinctly rather than presenting one "leveraged yield" number.
- **Realistic defaults deliberately show a very thin net yield (0.77%) and a strongly negative cash-on-cash return when leverage is on, and that is not a bug to tune away.** At a representative 3% gross yield (₹12,500/mo rent on a ₹50L property — the same numbers `rent-vs-buy` uses, chosen for cross-tool consistency) with realistic operating costs, net yield collapses to under 1% — a genuine, defensible feature of Indian residential real estate economics (low yields, real carrying costs), not a modeling error. This is exactly the "interpret, don't dump" insight the tool exists to surface, and FAQ #2 names the low-yield phenomenon directly.
